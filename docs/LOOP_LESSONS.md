# Loop 已证实的反例

只记录真实返修、错误验收或验证遗漏。每条依次写规则、原因、可复核证据，并注明独立观察日期。证据写明发生阶段、适用版本、原始异常、修正动作及实际核对结果，未确认的原因和验证范围单列。同一次问题在多份文档或日志中出现只算一次；同类问题在三个不同日期出现后，考虑提炼为项目规范。保留首次失败及后续修复范围，同期开发中可先记实证，后续证据由原文档写者追加。公开记录只链接可公开的源码、测试、文档、PR 或 Release，删去私人路径、身份、游标、私有日志、用户内容和凭据。不新增定时任务。格式参考 [Magpie 的复盘记录](https://github.com/yetone/magpie/blob/235f50a7a83269ff3411265fbdc4db4af161d812/LESSONS.md#L2-L9)。

## 投递路径名不能当作接收回执（2026-11-23）

- **规则：** 投递路径或回执变更时，同一 PR 核对代码、行为文档、操作指南和离线 Skill 的描述。分别记录选路、事件提交和目标控件接收，不用前一环替后一环。
- **原因：** 微信兼容路径改用 `clipboard_final` 后，仓库 CLI 指南和离线排查流程仍把 `wechat_menu_paste` 当成当前路径。选路时就会写入 `input.method`，之后仍可能取消或失败。独立复核还发现，面板和 CLI 听写跳过[自动捕获](../crates/voiceport-macos/src/controller.rs)，所以 `status` 可能沿用前一轮投递的路径和失败阶段。
- **证据：** 执行基线 `91bc8d146cdee8a5b70200da89094dd081e0524b` 中，`git grep -n wechat_menu_paste 91bc8d1 -- docs/CLI.md skills/voiceport/references/` 同时显示两处过时说明和一处已正确标旧版的说明。[选路实现](../crates/voiceport-macos/src/delivery.rs)的 `Delivery::accept_capture` 在实际提交前设置 `clipboard_final`；[回执回归](../crates/voiceport-macos/tests/delivery_receipt.rs)的 `clipboard_submission_is_not_confirmation_and_uncertainty_cannot_retry` 区分提交与确认。历史[合成目标记录](INPUT_DELIVERY.md#验证范围)证明专用控件能收到文字，不证明真实微信聊天框接收。本次只纠正文档，不改变投递代码。

独立观察：1 次（2026-11-23）。

## 启动批次与开发并行分别核对（2026-11-25）

- **规则：** 用户明确要求就绪工项并行时，按授权及资源预算在独占 worktree 启动各个任务。启动请求可分批，重型验证与共享桌面的 GUI 检查按资源互斥。逐会话记录启动、绑定和领取、实际落码与验证证据。见 [分派规则](LOOP_METHODS.md#31-一个逻辑问题多个独立归属的工作任务)和[逐会话核对](LOOP_EXECUTION.md#并行开发的逐会话核对)。
- **原因：** 默认批次被当成开发并发上限，已登记的部分任务未按用户要求启动。补齐启动后，活动会话之间也处在不同阶段，单看 `working` 无法确认每个工作区已落码。
- **证据：** 保留原 Run 和已登记任务，在各自独占 worktree 补齐余下启动，逐项读回启动及任务关联。随后对照各会话最新工具回执，确认一部分已写入产品源码，其余证据仍处在绑定、领取、查找入口或开始实现阶段。观察只覆盖当时的逐会话进展，后续写入、独立验证和集成须以各自回执为准。

独立观察：1 次（2026-11-25）。

## LoopX 登记成功须核对身份列表（2026-11-25）

- **规则：** 先用单身份预检确认参数形态，批量登记时每个身份各传一次 `--agent-id`。预检与执行后分别核对预期列表和实际项目、全局登记，再按具名 lane 预览。见 [LoopX 登记与领取](LOOP_EXECUTION.md#loopx-登记与领取)。
- **原因：** 一次逗号形式的 `--agent-id` 请求返回 `ok` 和 `registration_readback.verified`，但请求、项目和全局的三份身份列表均为空，具名预览仍为 `legacy_unscoped`。空列表也能满足所查 CLI 2.4.0 的列表一致性判据。原调用为何产生空请求列表仍待确认。
- **证据：** 改为每个身份各传一次 `--agent-id` 后，逐项读回三个列表，预期身份全部匹配，具名预览返回 `activation_state=selected`。这次修正的证据到登记和预览为止。可公开核对的发行范围为 2.4.0 至 2.4.1，已核对 2.4.0 发行包的登记逻辑。原失败回执所用的精确版本、其他版本受影响的范围和上游修复状态未确认。[LoopX 公开发行记录](https://pypi.org/project/loopx/#history)

独立观察：1 次（2026-11-25）。

## 签名通过后仍须扫描最终 ZIP（2026-11-25）

- **规则：** 对最终 ZIP 解包并检查文件范围和隐私内容。候选重建后，对新 ZIP 完成验签、升级连续性、版本、文件范围和隐私复查。将远端暂存和公开后的资产摘要与实测清单比对。见 [发布包隐私扫描与重新验签](LOOP_EXECUTION.md#发布包隐私扫描与重新验签)。
- **原因：** v0.3.14 的首次候选通过签名和升级连续性检查，随后解包扫描发现二进制内含带本机信息的 Rust 依赖源码路径。签名检查与内容隐私扫描各自覆盖不同风险。
- **证据：** 从同一冻结源码启用 `--remap-path-prefix` 重建并签名，保留首次回执，在独立目录解包复查签名、上一版签名要求、版本、文件范围和私有路径。先暂存附带全部资产的 Release 并复核 SHA-256，公开后读回标签与摘要，和实测资产一致。本次为自签名开发预览，正式 Developer ID 公证的范围见 [正式发布与首次配置](MACOS_UPDATES.md#正式发布与首次配置)。[v0.3.14 Release](https://github.com/forwaryan/voiceport/releases/tag/v0.3.14)

独立观察：1 次（2026-11-25）。

## 补丁退出 0 后仍须核对物化（2026-11-25）

- **规则：** 从获准工作区的实际 Git 根应用冻结补丁，对照交付清单逐项核对实际字节、模式和差异。见 [冻结补丁的实际物化](LOOP_EXECUTION.md#冻结补丁的实际物化)。
- **原因：** 在嵌套 Git 目录应用时退出 0，预期字节仍未物化。Git 从子目录运行时可能跳过目录范围外的补丁路径。
- **证据：** 原尝试的退出码与工作区实际字节不一致。隔离样例中，从更深的子目录执行 `git apply --verbose` 返回 0 并报告 `Skipped patch`，待改文件字节保持原值。从对应 Git 根应用同一补丁后，才得到预期差异和文件字节。

独立观察：1 次（2026-11-25）。合成样例只复核 Git 的跳过机制。

## 原生焦点保持须建立 key window 正基线（2026-11-25）

- **规则：** 对专用合成目标分别记录 key window、AX 焦点和光标的正基线及前后比较。key window 前后均为 `nil` 时，记录该项未覆盖。见 [原生焦点与分块输入反例](LOOP_EXECUTION.md#原生焦点与分块输入反例)。
- **原因：** 隔离 overlay 夹具的 AppKit 窗口没有成为 key window。此时比较前后两个空值会掩盖 key window 前置条件缺失。
- **证据：** 定向库测试、合成 Controller 回归和原生 overlay 焦点夹具依次退出 `0/0/78`。原生夹具观测到目标的 AX 焦点、first responder 和插入位置不变，应用未取得 key window，夹具目标也未成为 key。完整原生焦点验收仍缺证据，须在能为同一专用合成目标建立 key 正基线的授权隔离 GUI 会话复跑。

独立观察：1 次（2026-11-25）。

## 共享 provider 拒绝过期修订后先核对写入（2026-11-25）

- **规则：** 明确的 CAS 修订拒绝先查原 operation ID 和实际状态。确认未写入后，以当前修订、同一 operation ID 和原请求内容有界重试，再读回本 lane 结果。见 [共享 provider 修订冲突](LOOP_EXECUTION.md#共享-provider-修订冲突)。
- **原因：** 并行 lane 向同一 canonical Goal 的 provider 写入需求。先读到的修订在 refine 实际写入前已过期。
- **证据：** 首次 refine 返回 `goal_acceptance_provider_revision_mismatch`，读回确认没有该 lane 的本次需求写入。改用当前修订和原 operation ID 重试，回执为 `status=applied`，随后从 canonical 来源读回本 lane 的需求和 Todo 关联。该次恢复只覆盖明确拒绝且证实未落地的操作。未知副作用按原回执诊断，其他 lane 的写入仍按原归属。

## 分块切焦反例在首片与后续轮询之间设置（2026-11-25）

- **规则：** 在提交入口返回后确认首片已到目标，随后设置合成失焦，再推进首次外部轮询。验证剩余片段和重复回调均未新增写入。见 [原生焦点与分块输入反例](LOOP_EXECUTION.md#原生焦点与分块输入反例)。
- **原因：** `ChunkedInput::submit` 同步调用 `poll_inner`。在目标就绪的夹具中，首片在提交入口内已写入。把切焦安排在首次外部轮询后，第二片也可能已提交。
- **证据：** 首次用例在模拟切焦前已看到两个标量，Cargo 退出 `101`。将切焦移至 `deliver_inner` 返回后、首次外部轮询前，两次矩阵运行均通过，合成目标只收到首片。结果覆盖合成目标的提交时序、失焦拦截和重复回调，真实 Orca、WebKit 或终端控件接收另需授权实测。

独立观察：1 次（2026-11-25）。

## 恢复接入和退出清理须在实际阻塞阶段验证（2026-11-26）

- **规则：** 在替代设备打开或复核已进入后改变合成权限或默认设备，核对接入、最终转写和失败回执。默认输入组合查询的探针要在 ID 已取出、设备详情仍在读取时切换默认，保持两台设备可用。另验证最终 ID 读出后、接纳前送达的变化通知。验证退出清理时，先证明录音缓存已创建且输入释放已阻塞，由父进程在子进程退出后、夹具清理前核对缓存。
- **原因：** #47 首轮冻结候选在恢复打开前读取权限，打开返回后直接接入。原退出夹具卡在创建缓存前，并在退出前主动清理夹具目录，漏过了停止阶段仍持有 AAC 和租约的情况。
- **证据：** 两轮独立合成探针分别读回了撤权后的替代输入接入与 AAC 提交，以及原生 Quit 后残留的 AAC、会话标记与租约。第二次定向返修前，独立探针两次在组合查询的详情阶段切换默认输入。即使两台设备仍可用，过期设备仍被接入，实际 CLI 停止后提交了通过 AAC 校验的录音。修正后的[音频夹具](../crates/voiceport-macos/src/app/control/fixture/audio_start.rs)复用真实 CLI 和 AppKit，分别检查首次接入、恢复接入、停止超时和子进程退出后的实际磁盘状态。现场麦克风和系统授权另需授权实测。

独立观察：1 次（2026-11-26）。

## 同一 UID 的原生验证按实际释放逐项交接（2026-11-26）

- **规则：** 独占 worktree 可以并行开发。同一 effective UID 下的原生重验由协调者按主机锁顺序交接。分别保存检查是否启动、runner 退出与子进程组清理，以及主机锁和 checkout 锁释放的读回，再给下一项分配时段。 [验证资源范围](LOOP_EXECUTION.md#验证逐项写盘退出与清理分开记录)
- **原因：** 工作台功能候选同时准备时，早期锁冲突发生在检查启动前。设备复验完成后的首次释放探测又误读了报告字段，缺少对子进程组的实际核对。
- **证据：** 设备候选的上一轮恢复夹具退出 `101`。修正自动语言输入后，精确冻结候选的设备恢复、电平和私有 IPC 三条检查均退出 `0`。按 [runner](../scripts/verification_run.py) 启动子进程时记录的 PID 查验各自进程组，均无剩余成员；对两把锁的 `lsof` 均退出 `1`，无持有者，随后完成交接。该报告覆盖设备候选定向复验。工作台正常导航、原生焦点和整批量化对照仍需各自的实际证据。

独立观察：1 次（2026-11-26）。
